# Localize a template

Keep language versions in one shared block tree with `settings.locales` and `l10n`. For independent layouts, keep separate templates and switch with `editor.load(id)`.

**Read first:** [cli.md](cli.md) for the pinned invocation and exit codes; [version-awareness.md](version-awareness.md) for the installed SDK version.
**Consult:** [providers.md](providers.md) for `localization`, `localization.doNotTranslate`, `translation` and collaboration config. Fetch the page for the job through [docs.md](docs.md):

| Job | Page | Self-check |
|---|---|---|
| Turn on versions, add and edit a language, check and render it, subject lines | `guide/localized-templates` | `validate <file> --locale <tag>` |
| Translate with a provider: masking, do-not-translate, limits, errors, DeepL | `backend/translation` | `runTranslationConformance` |
| Exchange strings as files from the CLI | `api/template-tools` (Strings) | `strings import` exit code and its `rejected` list |
| Exact declarations of the types and pure helpers | `api/types` | — |
| Locale operations, `setDefaultLocale`, guards and locks | `api/operations` | the shared operation fixtures, then `validate` |

## Configuration and compatibility

`init({ localization: { locales: ["en", "de", "fr"] } })` turns on language versions. Existing templates need no migration, and configuration alone writes no localization fields. Keep every `@templatical/*` package on one version: an older renderer renders the default language and an older validator rejects `l10n`. A self-built collaboration backend must apply the locale operations and lock `locale` ([providers.md](providers.md)); until it does, it rejects them as `invalid_operation`. A self-built comments backend stores and returns `Comment.locale`. The Cloud editor does not support language versions yet: `initCloud()` ignores the key and logs a warning.

`settings.locale` is the default; change it only with `setDefaultLocale` (see "Change the default language" below). `settings.locales` contains other versions without duplicates or the default. A stored version absent from `localization.locales` is selectable but read-only, marked **Not enabled**; value edits and structure changes are refused. `getLocale()`, `setLocale(tag)` and `onLocaleChange(tag)` control view state, which starts at the default and is not saved. An unknown version throws `unknown_locale`.

Imported languages from [Beefree](https://docs.templatical.com/guide/migration-from-beefree), [Unlayer](https://docs.templatical.com/guide/migration-from-unlayer) and [Topol](https://docs.templatical.com/guide/migration-from-topol) use these same layers. Every importer accepts `defaultLocale?: string`, used only when the source declares no default; the CLI forwards `import --default-locale <tag>` and exits 2 for an invalid tag. A declared default or `defaultLocale` that isn't a language tag, such as `{{lang}}`, is ignored with a warning naming it, and the next valid value or `"en"` applies. Unlayer JSON has no default language: supply the host's configured default or the importer assumes `"en"` and warns for multilingual designs. Inspect `report.warnings` for dropped languages or fields, configure `localization.locales` with the imported languages, then run `template-tools validate imported.json --locale <tag>`.

## Language values

1. Add a language with **Languages → Add language**, or the `addLocale` operation. Remove with **Remove {language}** or `removeLocale`; removal drops its block and settings layers and is undoable in the editor. Labels name each language in itself (**Deutsch**, **Français**).
2. Write translated text with `updateBlockLocale.text` and `sourceHash: sourceHash(defaultValue)`. Use `set` for URLs, image sources, styles and other overrides, or `hidden: true` to omit a block in this language. Use `updateSettingsLocale` for preheader text and settings overrides such as direction. A text path must name an existing translatable field; `set` may add an optional property when its parent exists. `null` in `set` means absence. Omit empty localization members.
3. In a language view, text and property edits affect that version. Existing default text produces `text` with `sourceHash`; an absent default such as a missing preheader produces `set`, without staleness tracking. An equal value leaves no override. The settings panel shows a language pill and a **Reset to {default}** icon that restores one field and preserves sibling overrides. The status badge’s **Reset changes** clears all of that block’s `set` overrides and keeps its `text` translations. Structure edits affect every version; **Structure changes apply to every language.** appears once per session per template. A disabled version refuses these edits.
4. Check missing/stale values and merge tags, then render the selected locale. Each block's status badge in its top-right corner (top-left in right-to-left content) shows an icon whose tooltip and accessible name give the label: the first of **Hidden in {language}**, **Not translated**, **Out of date**, **Merge tags differ** and **Changed in {language}**; **Jump to block** on a localization finding opens it. **Merge tags differ** marks a current translation whose tags differ; its **Re-translate** (with a provider) sends every eligible text field of that block, and **Use {default}** removes only the mismatched translations.

Property paths use `.` and element ids, not array indices: `items.nav-shop.text`, `rows.row-one.cells.cell-one.content`, `fieldValues.heading`, `styles.padding`. Field ids are `<blockId>/<path>` or `settings/<path>`. `TRANSLATABLE_FIELDS` and `translatableFields(block, definitions)` identify text; custom blocks cover only `text` and `textarea`. Menu item, social icon, table row and table cell ids must not contain `.` or `/`; validation reports them, and `addBlock`, `updateBlock` and `setContent` refuse an operation that adds one. An id already on its block stays editable; rename it to localize that element. Use `elementIdIssues(content)` to inspect their template paths. Language tags must match `^[A-Za-z]{2,3}(-[A-Za-z0-9]{2,8})*$`: 2–3 ASCII letters, followed by zero or more hyphen-separated subtags of 2–8 ASCII letters or digits. Forms beginning with `x-…` or `i-…` are rejected because their language segment has one letter; grandfathered forms such as `no-bok` and `zh-min-nan` match and are accepted.

For a standalone Node TypeScript example with `@templatical/types` and `@templatical/renderer` installed, fetch `https://docs.templatical.com/guide/localized-templates.md`. Its complete authoring example creates a default title, runs `addLocale`, `updateBlockLocale` and `updateSettingsLocale` through `applyOperations`, and renders German. Save the original content with its layers, not the result of `resolveLocale`.

`unset` resets field paths; `expect` guards fail with `precondition_failed`, and invalid operations or paths are `invalid_operation`. Generic `updateBlock`/`updateSettings` refuse localization fields; `addBlock` may carry layers and `setContent` replaces the whole document. `invertOperations` creates the guarded inverse. `validateTemplate` validates every declared language’s resolved blocks and settings against the ordinary schemas, naming the locale on errors. Fetch `api/operations` for application order, pruning and undo guards.

## Translate a language

1. Check the installed SDK version, then fetch `backend/translation` and `guide/localized-templates` through [docs.md](docs.md). Pass a `TranslationProvider` as `init({ translation })`, alongside `localization`. Translate appears only in an enabled non-default language view; no loaded template or `AiProvider` is required. `initCloud()` ignores `translation` with a warning.
2. Select the version and use **Translate {count} fields** in the language bar. The default is gaps only (missing and stale); current translations and manual edits survive. **Translate everything again…** overwrites all eligible fields after confirmation naming the field count and explaining replacement of manual edits. Open a block’s status badge for **Translate** and **Re-translate**. The gaps action is hidden at zero; Translate everything again is disabled when no fields are eligible.
3. Preserve the editor's mask: `<x id="n"/>` in text, `__xn__` in HTML attribute values, one shared id sequence per field, covering merge tags, logic tags and `localization.doNotTranslate` terms. Every id must return exactly once; original tags are restored byte for byte. `tags_changed` keeps the previous value. If a stored translation's tags no longer match, the old translation is not sent and the field is translated from the current default. HTML blocks, empty defaults, `set` overrides and hidden blocks are not sent. Batch limits, error codes and the sanitizer are in `backend/translation`.
4. Read the dismissible result notice: translated fields, old text retained, omitted fields, blocks skipped because they are locked and provider errors. It appears in the language bar. Cancel keeps valid fields already returned. Dismiss to show coverage again; changing views clears the result. **Back to {default}** returns to the default language. A run is one undo step, an ordinary edit under collaboration, and skips other sessions' locks in the captured target language or structurally. No change records no history; a second run rejects with editor-local `translation_running`.
5. Save and run the pinned CLI below: `validate --locale de`. Require no `localization.untranslated` or `localization.stale` after translating eligible fields, and no `localization.merge-tags-differ`. Inspect issues even on exit 0: missing/stale warnings are advisory. Manually translate excluded fields if needed.

For brand names, configure `localization.doNotTranslate` using [providers.md](providers.md); terms share the tag placeholder check, so preservation is checked on return, not asked of the model. Pass the same list to `localeStrings` and `applyLocaleStrings`, or `--do-not-translate <file>` to both CLI `strings` commands.

For a backend, use `createHttpTranslationProvider({ url, headers?, fetch? })` from `@templatical/ai-kit/client`, `readTranslationRequest` and `translateFields` from `/server`, or implement the plain provider for DeepL/TMS. Fetch `backend/translation` for the wire, limits, exact signatures, the DeepL settings and the runnable server example. Run `runTranslationConformance` from `@templatical/ai-kit/testing`; the `createMockTranslationProvider` is deterministic.

For CLI exchange, use `strings export template.json --locale de --out strings.de.json`, translate the entries’ `text`, then `strings import template.json strings.de.json --json`, using the pinned invocation and flags from [cli.md](cli.md). A stale entry has no `text`; its old translation is in `previous`, which import never reads, so write `text` from `source` or it stays stale. Import re-masks current defaults and rejects `stale`, `tags_changed`, `unknown_field`, `not_translatable` and `unsafe_html` (markup outside the allowed tags and URL schemes, or not in the default of a `text` field); accepted fields are written even on exit 1. Both commands refuse the default language (exit 1); a file whose `sourceLocale` isn't the current default exits 2 with nothing written, so export again after `setDefaultLocale`. For the library route, `localeStrings(content, locale, { syntax, only: "gaps" })` → JSON → `applyLocaleStrings` with the original tokens and extraction-time `sourceHash` returns locale operations for `applyOperations`; the pure helpers do not sanitize external HTML. A stale entry's `text` is its stored translation, and applying it unchanged marks the field current (like **Keep**): drop `text` from stale entries before handing the JSON to a translator (with `only: "gaps"`, only stale entries carry `text`; with `only: "all"`, `localeCoverage(content, locale).stale` lists them), or use `strings export`. Fetch the guide’s CI-run snippet.

A subject line is host-owned, not in the template: translate it with the same provider as one `text` field, masked with `maskTags(text, syntax, "text", { doNotTranslate })` and restored with `unmaskTags(text, tokens)`, which returns `null` when a placeholder is missing or changed. Fetch the guide's "Subject lines" snippet.

AI chat, Fix, Rewrite and alt text use the active language: added text becomes default content, structure changes stay shared, and whole-template replacement and `setDefaultLocale` are refused in language views. Fetch `backend/ai` for the AI gates and request fields.

## Missing, stale and merge-tag checks

| Rule | Action |
| --- | --- |
| `localization.untranslated` | Missing nonempty default text falls back to the default; **Not translated** marks it. Write a translation or accept the advisory warning. Hidden blocks and empty defaults are excluded. HTML blocks are included but never sent by Translate or `strings export`: translate them by hand, or the warning stays. |
| `localization.stale` | **Out of date** means the stored `sourceHash` differs from `sourceHash(defaultValue)`. **Keep** updates the hash while retaining the existing text entry, including when the new default equals it; coverage counts it as translated. Hide and Show also preserve text entries; **Use {default}** removes the field's value to restore fallback. Sibling overrides remain. |
| `localization.merge-tags-differ` | Preserve the default's merge-tag multiset, including repeated occurrences. This warning is blocking in CLI validation. |

For an existing saved `template.json`, run:

```bash
npx -y @templatical/template-tools@0.51.1 validate template.json --locale de --json
npx -y @templatical/template-tools@0.51.1 render template.json --locale de --format mjml --out template.de.mjml
```

Missing/stale warnings alone allow exit 0; merge-tag mismatches cause exit 1 even with `valid: true`. An unknown locale exits 1 with `unknown_locale` on stderr and no result document, including with `--json`. A missing or empty `--locale` value exits 2. If lint itself throws, validate exits 2 with a diagnostic on stderr and no result document. `--format html` needs the optional `mjml` dependency (exit 3 if absent). Read every issue, not just `valid`.

Headless `lintTemplate(content, { contentLocale: "de", locale: "en" })` checks German and returns English messages. Dictionaries remain a union across languages; `contentLocale` is not a spelling/dictionary locale. `localization.rules` overrides severity, and `localization: false` disables the category.

## Change the default language

In the editor: **Languages** → the version's **More actions for {language}** → **Make default language**, then **Make default** in the dialog, which counts the fields without text in that language. It is one undo step, and the view moves to the new default. The item is disabled, with its reason, while the current default isn't in `localization.locales` ("Add {default} to the enabled languages first": the old default would become a read-only version) and while blocks are hidden in that language; it is absent in a read-only editor or for a version that isn't enabled. With collaboration, its Undo is skipped once this editor has received another session's batch after it; a batch the backend committed but hasn't delivered is caught by the backend, which refuses a batch with a `setContent` whose `baseRevision` isn't current (`409`, `precondition_failed`).

Headless or from the CLI, apply `{ "op": "setDefaultLocale", "locale": "de" }` (the `edit` command in [edit.md](edit.md)). Before it:

- `defaultLocaleGaps(content, "de", definitions?)` lists the field ids German has no text for. They keep the old default's value, and the old default keeps no copy of them. Afterwards `validate --locale en` reports them as `localization.untranslated`, and editing one in the new default changes the English email too. Translate them into German before the change (Translate in the German view, or `strings export --locale de` and `strings import`) until `defaultLocaleGaps(content, "de")` returns `[]`. Translate and `strings export` don't send HTML blocks or empty defaults: translate HTML blocks by hand in the German view; an empty default has no text to keep and isn't a gap.
- `localeHiddenBlocks(content, "de")` lists the blocks hidden in German. Any hidden block refuses the change with `invalid_operation`; show them first. An unknown version also gives `invalid_operation`, and another session's lock gives `locked_by_others`.
- From the CLI, without code: the `edit` refusal names only the number of hidden blocks (`2 blocks are hidden in "de". Show them before making it the default.`, exit 2, nothing written). List them with `jq '[.. | objects | select(.l10n?.de?.hidden == true) | .id]' template.json` and show each with `{"op":"updateBlockLocale","blockId":"<id>","locale":"de","hidden":false}`. Then `validate template.json --locale de --json` reports every gap as `localization.untranslated`, HTML blocks included, and `strings export template.json --locale de --out strings.de.json` exports the gaps except HTML blocks, together with out-of-date fields, which aren't gaps; set their `text` and run `strings import`. After the change, `validate template.json --locale en --json` lists the remaining gaps as `localization.untranslated`, and only those: a field German translated to the English text keeps a current entry in English.

The promoted version's values become the base; the former default becomes a version in the same list position. Other languages' current text is re-stamped and stays current; out-of-date text keeps its stored hash and stays out of date, unless that hash equals the promoted value, in which case it becomes current. `updateSettings` refuses to change `settings.locale` while versions exist, and AI in a language view can't run `setDefaultLocale`. The inverse restores the exact prior content. Fetch `api/operations` for re-stamping, optional-field removal and refusal messages, then run `template-tools validate`.

## Rendering and collaboration

A layout carries its own `settings.locales`, block `l10n` and `settings.l10n`, including wrapper children beside the slot. Rendering projects it for the requested language with `resolveLocale(layout, locale, { missing: "default" })` before composition, falling back to the layout's default when it lacks that language. A layer can't hide the layout's slot or a wrapper that contains it (`invalid_operation` from `updateBlockLocale`, and from `moveBlock` or `addBlock` placing the slot under a hidden block; `validate` reports it). The editor never edits the layout and Translate never sends it: translate the layout file with `edit --op '{"op":"addLocale","locale":"de"}'`, `strings export`, setting each entry's `text`, and `strings import`, then `validate layout.json --locale de`.

`renderToMjml(content, { locale: "de" })`, `editor.toMjml({ locale: "de" })` and `editor.toHtml({ locale: "de" })` select a version. Omission renders the default regardless of active view. `resolveLocale(content, "de")` is a pure projection: text and overrides applied, hidden blocks removed recursively, localization fields stripped, `settings.locale` set to `de`. The editor's HTML method still needs `render.toHtml` or `render.compileMjml`; local MJML needs the renderer peer.

Locks carry `locale?: string | null`, absent meaning null (default language and structure). Forward the optional locale through provider `acquireLock`, `renewLock`, `releaseLock` and `onUnlock`. A selection takes its lock in the active view's language (`null` in the default view), including a read-only **Not enabled** view, whose viewer holds (X, de) but can't edit. A localized edit on (X, de) conflicts with another session's (X, de) or (X, null) lock, while (X, fr) can coexist. `updateBlock`, `moveBlock` and `deleteBlock` conflict with every other session's lock on X (moves and deletes also with locks inside X), `addBlock` checks no locks, and `setDefaultLocale` conflicts with every lock. `onRemoteChange.locale` reports the first locale operation's language in the batch, excluding `setDefaultLocale`, otherwise null. A backend ignoring locale serializes per block; check the lock matrix against the contracts in `backend/collaboration` and the shared operation fixtures documented in `api/operations`.

Comments carry the view's language tag in `CommentInput.locale`, the default's included; an untagged comment, saved before language versions or by a comments backend that doesn't store `locale` (Cloud's doesn't yet), counts as the current default and follows a change of the default; a tagged comment keeps its tag. **This language** filters threads in the comments panel.

## Custom blocks

Pass `--definitions definitions.json` to CLI `validate`, `render`, `strings export` and `strings import` for custom text translations. It is a JSON array of `CustomBlockDefinition`, checked entry by entry; invalid input exits 2. Rendering uses each type’s Liquid template and stylesheet. For the library route use `validateTemplate(content, definitions)`, `lintTemplate(content, { customBlocks: definitions, contentLocale: "de" })` and `renderToMjml` with `renderCustomBlock` and `getCustomBlockStylesheet`. Fetch the complete library example through [docs.md](docs.md) → `guide/localized-templates`; CLI flags and file contracts are in [cli.md](cli.md).

Any `text` or `set` entry in a custom block's requested locale layer discards its default-language `renderedHtml`, keeping `renderedStylesheet`. A resolver renders the localized fields; without `renderCustomBlock` the block is omitted, including CLI renders without `--definitions`. Blocks without a layer for that locale retain cached HTML. Check the library example's validation result and localization issues, and verify the rendered MJML contains the translated custom text.

## Limits

- Column structure is shared across languages and can't be overridden per language. Column order follows each language's direction, so a right-to-left version shows the first column on the right, but explicit left and right text alignment and left/right padding aren't mirrored: override them per language.
- Text in a custom block's repeatable items can't be translated field by field, because the items have no ids. Override the whole `fieldValues.<key>` per language instead.
- Translate leaves out HTML blocks. Translate them by hand in the language view.
- Blocks the AI adds in a language view enter the shared tree with their text as default content, as a paste does. AI can't replace the whole template in a language view; switch to the default language for that.
- Comment threads are shared across languages. Each new comment and reply stores its view’s language tag through a BYO [comments provider](https://docs.templatical.com/backend/comments); Cloud does not store it yet. Version history remains per template, not per language.
- The Cloud editor doesn't support language versions or translation yet: `initCloud()` ignores `localization` and `translation` and logs a warning.
- Strings are exchanged as JSON; XLIFF and CSV aren't supported.
